## Implemented slice

- Grok CLI REST now parses the pin's actual protobuf-JSON `{val}` fields, uses the credits query, reads subscription identity before calling a zero cap exhausted, and preserves the single weekly pool. A failed `/v1/user` read yields no synthetic exhausted row (the pin treats an unknown tier as free and emits one); this difference is kept. The 401/403 authentication-expired outcome is kept. Fixture: `tests/unit/grok-cli-usage.test.js:21-59`. #224 adds the gRPC fallback, the plan labels and the remaining REST windows (PARITY §6.30).
- Kenari zero-capacity windows stay bounded at zero rather than becoming unlimited, using the field shape in `U/kenari.js:36-45` with synthetic numbers. DeepSeek balances (#212) are one credit window per currency carrying a `quota.Credit` (currency, state, amounts) and no remaining fraction: a zero balance is reported as zero, never unlimited, and a zero CNY balance cannot exhaust an account with positive USD credit because no currency is summed with or compared to another. Where the pin folds a missing or malformed amount to 0 and clamps a negative one (`U/deepseek.js:19-22,93`), Routeweft reports `missing`, `malformed` or `negative`; an unreported `is_available` is `DeepSeek (Availability Unknown)` rather than the pin's insufficient-balance label.
- `/admin/v1/quota` adds named `windows`, `plan`, and Codex `availableResetCredits`, while retaining the existing routing summary and pagination. It reads cached observations and makes no provider request.
- Session-gated GET `/admin/v1/quota/{id}/codex-reset-credits` returns the existing normalized balance/expiry listing. POST with `{"confirm":true}` spends one credit, using a server-generated UUID. Missing confirmation and non-Codex accounts fail before a network call. No-credit is 409; ambiguous provider failures are 502 without retry. The request cannot choose a target URL or replay ID.

## Opt-in generation warming

The pin has a generation scheduler, not just quota polling: `src/shared/services/quotaAutoPing.js:106-180,188-245,261-313`, with constants in `src/shared/constants/config.js:41-66`. Routeweft now accepts `claudeAutoPing` and `codexAutoPing` through session-gated PATCH `/admin/v1/settings`, using the existing string-valued `set` map. Each value is a JSON string representing `{"connections":{"connection-id":true}}`. Both default to `{"connections":{}}`, so warming is off until the operator selects accounts. Removing a setting disables its accounts. Only active OAuth connections for the matching provider are eligible.

A single worker checks every minute. Claude warms at reset (5-second lead tolerance); Codex requires a reset slide of at least 30 seconds, a 10-minute minimum interval, and no exhausted non-session windows. Unknown/exhausted sessions do not ping. Failures cool down for 15 minutes. Tiny request models/bodies follow the pin constants; Codex streams are drained before success. Successful reset-minute keys and timestamps persist in the existing SQLite `settings` table as `quotaAutoPingHistory` through compile/commit/publish; it is not generically writable. Tests cover opt-in, reset slides, blocking quota, failure cooldown, concurrent ticks, restart suppression, and wire/cancellation.

Residual: a crash after the provider accepts generation but before the history commit can repeat a ping after restart. A persistence failure suppresses repetition in the running process. Opt-in UI controls, named-window visibility, and migrated v1 opt-ins remain U06; this PR does not edit the migration contract. Warming can consume provider quota and is never enabled by quota refresh alone.

## Impact and verification

No inference hot-path code or accounting paths change, so no hot-path benchmark delta is claimed. No SQLite schema migration is added: only the existing settings table stores opt-ins and suppression records. Raw provider responses and credentials are not exposed by the quota admin read model. Reset actions use the credential registry and guarded HTTP client; failures return fixed messages. Quota helper/global-proxy parity remains open under the existing networking tracker.

Validation results are recorded in the PR description. Tests use scripted HTTP clients and sanitized fixtures; none call a live provider.
